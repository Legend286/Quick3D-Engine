# Q3DE Indirect Ray-Tracing Geometry and Surface Reconstruction Specification

## 1. Purpose

This system minimises ray-tracing geometry duplication by separating:

1. **intersection geometry**, required by hardware traversal;
2. **surface shading data**, fetched only after a ray hits a triangle.

The BLAS contains or references only:

* vertex positions;
* triangle indices or implicit triangle ordering;
* acceleration-structure metadata maintained by the graphics API.

The BLAS does not duplicate:

* UV coordinates;
* vertex normals;
* tangents;
* vertex colours;
* material parameters;
* texture handles;
* skinning weights;
* bone indices;
* previous-frame positions;
* arbitrary custom vertex attributes.

After a hardware triangle hit, Q3DE reconstructs the complete surface using:

```cpp
InstanceID
GeometryIndex
PrimitiveIndex
Barycentrics
```

This follows the same indirection model as the raster visibility buffer.

---

# 2. Important Limitation

A hardware triangle BLAS cannot store only a triangle ID.

The ray-tracing hardware still requires actual triangle positions to perform:

* bounding-volume traversal;
* ray-box intersection;
* ray-triangle intersection;
* closest-hit ordering.

The optimisation is therefore:

```text
Not:

BLAS = triangle IDs only

Instead:

BLAS = positions + triangle topology only

External buffers = every shading attribute
```

The compact hit identity is generated by hardware after intersection.

---

# 3. High-Level Pipeline

```text
Geometry import
    ↓
Canonical geometry database
    ├── position stream
    ├── index stream
    ├── normal/tangent stream
    ├── UV streams
    ├── colour/custom streams
    └── material mappings
    ↓
BLAS construction using positions and indices only
    ↓
TLAS instances reference BLAS objects
    ↓
Ray traversal
    ↓
Hardware triangle hit
    ├── instance ID
    ├── geometry index
    ├── primitive index
    └── barycentrics
    ↓
Q3DE SurfaceHit
    ↓
Geometry-table indirection
    ↓
Triangle index fetch
    ↓
Attribute fetch and interpolation
    ↓
Material resolution
    ↓
BSDF evaluation
```

# 4. Canonical Surface-Hit Representation

Both raster and ray tracing must resolve into the same engine-level structure.

```cpp
struct SurfaceHit
{
    uint instanceID;
    uint geometryID;
    uint primitiveID;
    float2 barycentrics;
};
```

Barycentric convention:

```cpp
float3 GetBarycentricWeights(float2 barycentrics)
{
    return float3(
        1.0 - barycentrics.x - barycentrics.y,
        barycentrics.x,
        barycentrics.y);
}
```

This gives weights for triangle vertices:

```text
vertex 0 = 1 - u - v
vertex 1 = u
vertex 2 = v
```

The convention must be identical throughout the renderer.

# 5. GPU Scene Tables

## 5.1 Instance table

Each TLAS instance exposes a compact instance identifier.

```cpp
struct GPUSceneInstance
{
    uint geometryGroupOffset;
    uint geometryGroupCount;

    uint materialOverrideOffset;
    uint transformIndex;

    uint previousTransformIndex;
    uint flags;

    uint sceneEntityID;
    uint rtMetadataOffset;
};
```

`InstanceID` or the API's custom instance index maps into this table.

The instance table provides:

* object transforms;
* previous transforms;
* geometry-table range;
* material overrides;
* dynamic/static flags;
* scene entity identity.

---

## 5.2 Geometry table

Each BLAS geometry maps to one Q3DE geometry record.

```cpp
struct GeometryRecord
{
    uint positionOffset;
    uint previousPositionOffset;

    uint indexOffset;
    uint primitiveOffset;

    uint normalOffset;
    uint tangentOffset;

    uint uv0Offset;
    uint uv1Offset;

    uint colourOffset;
    uint materialIndexOffset;

    uint vertexCount;
    uint primitiveCount;

    uint materialBase;
    uint flags;
};
```

The record contains offsets into global or bindless geometry buffers.

Offsets may represent:

* element indices;
* byte offsets;
* device addresses;
* bindless buffer handles plus offsets.

The exact representation depends on the RHI.

---

## 5.3 RT geometry mapping table

The API-provided `GeometryIndex` is local to a BLAS.

Use it to resolve the Q3DE geometry record.

```cpp
struct RTGeometryMapping
{
    uint q3deGeometryID;
    uint localPrimitiveBase;
    uint flags;
    uint reserved;
};
```

Each instance or BLAS record provides the base of its mapping range:

```cpp
uint mappingIndex =
    instance.rtGeometryMappingOffset +
    hardwareGeometryIndex;
```

Then:

```cpp
RTGeometryMapping mapping =
    RTGeometryMappings[mappingIndex];

uint geometryID =
    mapping.q3deGeometryID;
```

# 6. BLAS Geometry Contents

## 6.1 Static mesh BLAS

A static triangle BLAS references:

```text
Position buffer
Index buffer
Vertex count
Index count
Vertex stride
Position format
Index format
Geometry flags
```

No shading attributes need to be referenced by the acceleration structure.

Suggested position formats:

```text
float3 / RGB32F
float4 / RGBA32F where API alignment prefers it
```

Use compressed position formats only if the RT API directly supports them and quality is acceptable.

---

## 6.2 Animated mesh BLAS

An animated BLAS references the current compute-skinned position buffer.

```text
Compute animation
    ↓
Compute skinning
    ↓
Current skinned position buffer
    ↓
BLAS update/refit
```

The index buffer remains static.

The BLAS still does not reference:

* normals;
* tangents;
* UVs;
* skinning data;
* bone matrices.

---

## 6.3 Procedural geometry

A procedural AABB BLAS could provide more flexible indirection, but would require a custom intersection shader.

That path would lose the standard hardware triangle intersector and automatic triangle barycentrics.

Therefore:

```text
Conventional mesh geometry:
    use hardware triangles

Analytic or genuinely procedural shapes:
    use AABBs and custom intersection
```

Do not use procedural AABBs merely to avoid supplying positions to a triangle BLAS.

---

# 7. Primitive Identity

The hardware primitive index is normally local to one BLAS geometry entry.

It is not necessarily:

* global across the BLAS;
* global across the mesh;
* global across the scene;
* equivalent to the raster draw primitive ID.

Q3DE must explicitly map it.

```cpp
uint localPrimitiveID =
    hardwarePrimitiveIndex;

uint canonicalPrimitiveID =
    mapping.localPrimitiveBase +
    localPrimitiveID;
```

For most shading lookups, retaining both `geometryID` and local `primitiveID` is sufficient:

```cpp
SurfaceHit hit =
{
    instanceID,
    geometryID,
    localPrimitiveID,
    barycentrics
};
```

A canonical global triangle ID can be formed when useful:

```cpp
uint globalTriangleID =
    geometry.primitiveOffset +
    hit.primitiveID;
```

# 8. Triangle Index Reconstruction

For indexed geometry:

```cpp
uint triangleIndexOffset =
    geometry.indexOffset +
    hit.primitiveID * 3;

uint i0 = IndexBuffer[triangleIndexOffset + 0];
uint i1 = IndexBuffer[triangleIndexOffset + 1];
uint i2 = IndexBuffer[triangleIndexOffset + 2];
```

Apply the geometry's vertex base if indices are local:

```cpp
i0 += geometry.vertexBase;
i1 += geometry.vertexBase;
i2 += geometry.vertexBase;
```

For non-indexed triangle lists:

```cpp
uint i0 = geometry.vertexBase + hit.primitiveID * 3 + 0;
uint i1 = geometry.vertexBase + hit.primitiveID * 3 + 1;
uint i2 = geometry.vertexBase + hit.primitiveID * 3 + 2;
```

The geometry flags must identify the indexing mode.

---

# 9. Hardware Barycentrics

Hardware triangle intersection returns two barycentric coordinates.

```cpp
float2 bary = GetHardwareBarycentrics();

float3 weights =
    float3(
        1.0 - bary.x - bary.y,
        bary.x,
        bary.y);
```

These barycentrics can reconstruct any per-vertex attribute:

```cpp
float3 InterpolateFloat3(
    float3 a,
    float3 b,
    float3 c,
    float3 weights)
{
    return
        a * weights.x +
        b * weights.y +
        c * weights.z;
}
```

For ray tracing, these are triangle-space barycentrics and do not need screen-space perspective correction.

# 10. Surface Reconstruction

## 10.1 Surface resolver interface

```cpp
struct SurfaceResolveRequest
{
    SurfaceHit hit;

    float3 worldRayOrigin;
    float3 worldRayDirection;

    float rayT;
    float rayConeWidth;

    uint requestedAttributes;
    uint flags;
};
```

```cpp
struct SurfaceData
{
    float3 objectPosition;
    float3 worldPosition;

    float3 geometricNormal;
    float3 shadingNormal;

    float4 tangent;

    float2 uv0;
    float2 uv1;

    float4 vertexColour;

    uint materialID;
    uint instanceID;
    uint geometryID;
    uint primitiveID;
};
```

The resolver should support partial reconstruction through attribute masks.

---

## 10.2 Requested attribute mask

Not every ray needs every attribute.

```cpp
enum SurfaceAttributeFlags : uint
{
    SurfaceAttribute_Position        = 1 << 0,
    SurfaceAttribute_GeometricNormal = 1 << 1,
    SurfaceAttribute_ShadingNormal   = 1 << 2,
    SurfaceAttribute_Tangent         = 1 << 3,
    SurfaceAttribute_UV0             = 1 << 4,
    SurfaceAttribute_UV1             = 1 << 5,
    SurfaceAttribute_Colour          = 1 << 6,
    SurfaceAttribute_Material        = 1 << 7,
    SurfaceAttribute_PreviousPosition = 1 << 8
};
```

Examples:

```text
Opaque shadow ray:
    no attributes

Alpha-tested shadow ray:
    UV0 + material

Diffuse GI ray:
    position + geometric normal + material

Full reflection ray:
    all shading attributes
```

This is important because the real optimisation is not only keeping data out of the BLAS—it is also avoiding unnecessary attribute fetches after intersection.

# 11. Position Reconstruction

## 11.1 Vertex-based position reconstruction

```cpp
float3 p0 =
    PositionBuffer[geometry.positionOffset + i0];

float3 p1 =
    PositionBuffer[geometry.positionOffset + i1];

float3 p2 =
    PositionBuffer[geometry.positionOffset + i2];

float3 objectPosition =
    p0 * weights.x +
    p1 * weights.y +
    p2 * weights.z;
```

Then:

```cpp
float3 worldPosition =
    TransformPoint(
        instance.objectToWorld,
        objectPosition);
```

---

## 11.2 Ray-equation position

The hit point can also be calculated using:

```cpp
float3 worldPosition =
    worldRayOrigin +
    worldRayDirection * rayT;
```

This avoids fetching positions solely to obtain the hit point.

However, triangle positions may still be needed for:

* geometric normals;
* derivatives;
* previous-frame positions;
* custom interpolation.

Recommended policy:

```text
Use ray origin + direction × hit distance for world position.

Fetch triangle positions only when another requested attribute requires them.
```

---

# 12. Geometric Normal Reconstruction

The geometric normal is derived from triangle positions:

```cpp
float3 edge0 = p1 - p0;
float3 edge1 = p2 - p0;

float3 objectGeometricNormal =
    normalize(cross(edge0, edge1));
```

Transform to world space using the correct normal transform:

```cpp
float3 worldGeometricNormal =
    normalize(
        TransformNormal(
            instance.objectToWorld,
            objectGeometricNormal));
```

Account for:

* negative determinant transforms;
* triangle winding;
* front-face state.

```cpp
if (!hardwareFrontFace)
{
    worldGeometricNormal =
        -worldGeometricNormal;
}
```

The exact front-face convention must be standardised across APIs.

---

# 13. Shading Normal Reconstruction

Fetch vertex normals externally:

```cpp
float3 n0 =
    DecodeNormal(
        NormalBuffer[geometry.normalOffset + i0]);

float3 n1 =
    DecodeNormal(
        NormalBuffer[geometry.normalOffset + i1]);

float3 n2 =
    DecodeNormal(
        NormalBuffer[geometry.normalOffset + i2]);
```

Interpolate:

```cpp
float3 objectShadingNormal =
    normalize(
        n0 * weights.x +
        n1 * weights.y +
        n2 * weights.z);
```

Transform:

```cpp
float3 worldShadingNormal =
    normalize(
        TransformNormal(
            instance.objectToWorld,
            objectShadingNormal));
```

Ensure it remains in the same hemisphere as the geometric normal:

```cpp
if (dot(worldShadingNormal, worldGeometricNormal) < 0.0)
{
    worldShadingNormal =
        -worldShadingNormal;
}
```

Normal mapping is applied later during material evaluation.

---

# 14. Tangent Reconstruction

Fetch packed tangents:

```cpp
float4 t0 =
    DecodeTangent(
        TangentBuffer[geometry.tangentOffset + i0]);

float4 t1 =
    DecodeTangent(
        TangentBuffer[geometry.tangentOffset + i1]);

float4 t2 =
    DecodeTangent(
        TangentBuffer[geometry.tangentOffset + i2]);
```

Interpolate:

```cpp
float3 objectTangent =
    normalize(
        t0.xyz * weights.x +
        t1.xyz * weights.y +
        t2.xyz * weights.z);
```

Interpolate or select handedness:

```cpp
float tangentSign =
    sign(
        t0.w * weights.x +
        t1.w * weights.y +
        t2.w * weights.z);
```

Transform and orthogonalise:

```cpp
float3 worldTangent =
    normalize(
        TransformDirection(
            instance.objectToWorld,
            objectTangent));

worldTangent =
    normalize(
        worldTangent -
        worldShadingNormal *
        dot(worldTangent, worldShadingNormal));
```

Bitangent:

```cpp
float3 worldBitangent =
    cross(worldShadingNormal, worldTangent) *
    tangentSign;
```

---

# 15. UV Reconstruction

```cpp
float2 uv0 =
    UV0Buffer[geometry.uv0Offset + i0] *
        weights.x +
    UV0Buffer[geometry.uv0Offset + i1] *
        weights.y +
    UV0Buffer[geometry.uv0Offset + i2] *
        weights.z;
```

The same applies to additional UV sets.

UV data may use:

* `float2`;
* packed half floats;
* quantised mesh-relative formats.

The surface resolver is responsible for decoding the storage format.

---

# 16. Material Resolution

Material identity can be stored at different granularities.

## 16.1 One material per geometry

```cpp
uint materialID =
    geometry.materialBase;
```

This is the cheapest path.

---

## 16.2 One material per primitive

```cpp
uint materialID =
    PrimitiveMaterialBuffer[
        geometry.materialIndexOffset +
        hit.primitiveID];
```

This enables several materials inside one geometry record.

---

## 16.3 Instance material overrides

```cpp
if (instance.HasMaterialOverride)
{
    materialID =
        ResolveMaterialOverride(
            instance.materialOverrideOffset,
            materialID);
}
```

The BLAS does not need to know the final material identity unless geometry flags such as opacity classification require separate geometry entries.

---

# 17. Opaque and Alpha-Tested Geometry

Geometry should be divided by traversal behaviour.

## 17.1 Opaque geometry

Mark geometry opaque where possible.

Benefits:

* hardware can skip any-hit shaders;
* traversal can accept intersections directly;
* shadows become cheaper;
* fewer attribute fetches.

---

## 17.2 Alpha-tested geometry

Alpha-tested geometry requires enough reconstruction to determine opacity.

Typical any-hit flow:

```text
Hardware hit
    ↓
Resolve geometry and triangle
    ↓
Fetch UV0
    ↓
Resolve opacity material
    ↓
Sample alpha texture
    ↓
Accept or reject intersection
```

The any-hit shader should fetch only:

* triangle indices;
* UV coordinates;
* opacity texture/material data.

Do not reconstruct normals, tangents or full BSDF data inside any-hit.

---

## 17.3 Transparent geometry

Fully transparent refractive or blended geometry generally requires explicit ray-tracing material logic.

It should not be treated identically to alpha-tested cutouts.

---

# 18. Geometry Partitioning Strategy

A BLAS may contain multiple geometry entries.

Partition geometry when there are meaningful differences in:

* opacity behaviour;
* index or vertex buffers;
* position formats;
* material classes;
* build flags;
* update frequency.

Avoid creating one BLAS geometry per tiny meshlet unless profiling demonstrates a benefit.

Excessive geometry entries can increase:

* BLAS build metadata;
* build time;
* shader-table or mapping complexity;
* geometry-index lookup overhead.

Recommended starting point:

```text
One BLAS per mesh or skinned mesh instance.

One geometry entry per submesh or opacity class.
```

# 19. Shared Raster and Ray-Tracing Geometry Database

The same `GeometryRecord` should support raster visibility reconstruction and RT reconstruction.

## 19.1 Raster hit

Raster visibility returns something resembling:

```cpp
struct RasterVisibilityHit
{
    uint instanceID;
    uint geometryID;
    uint primitiveID;
    float2 barycentrics;
};
```

## 19.2 Ray-tracing hit

Hardware RT returns:

```cpp
struct HardwareRTHit
{
    uint customInstanceID;
    uint geometryIndex;
    uint primitiveIndex;
    float2 barycentrics;
};
```

Map RT hit:

```cpp
SurfaceHit ConvertRTHit(HardwareRTHit rtHit)
{
    GPUSceneInstance instance =
        SceneInstances[rtHit.customInstanceID];

    RTGeometryMapping mapping =
        RTGeometryMappings[
            instance.rtGeometryMappingOffset +
            rtHit.geometryIndex];

    SurfaceHit result;

    result.instanceID =
        rtHit.customInstanceID;

    result.geometryID =
        mapping.q3deGeometryID;

    result.primitiveID =
        mapping.localPrimitiveBase +
        rtHit.primitiveIndex;

    result.barycentrics =
        rtHit.barycentrics;

    return result;
}
```

Both raster and RT then call:

```cpp
SurfaceData ResolveSurface(
    SurfaceHit hit,
    SurfaceAttributeFlags requestedAttributes);
```

# 20. Dynamic and Skinned Geometry

## 20.1 Current positions

Compute skinning writes:

```text
CurrentSkinnedPositionBuffer
```

This buffer is used by:

* raster visibility;
* BLAS update;
* geometric-normal reconstruction;
* surface-position reconstruction.

---

## 20.2 Previous positions

Previous positions remain outside the BLAS:

```text
PreviousSkinnedPositionBuffer
```

They are used for:

* motion vectors;
* temporal reprojection;
* previous-frame hit reconstruction;
* velocity-dependent effects.

The BLAS requires only current positions.

---

## 20.3 Update ordering

```text
GPU animation evaluation
    ↓
GPU compute skinning
    ↓
Storage/UAV barrier
    ↓
BLAS update or refit
    ↓
Acceleration-structure barrier
    ↓
Ray tracing
```

---

# 21. BLAS Update Policy

Use update/refit when:

* topology is unchanged;
* index data is unchanged;
* only positions move;
* the BLAS was created with update support.

Use rebuild when:

* topology changes;
* geometry entry counts change;
* index buffers change;
* deformation has significantly degraded BVH quality.

Suggested initial policy:

```text
Static mesh:
    build once

Skinned mesh:
    refit/update every relevant frame

Heavily deforming mesh:
    periodic rebuild after profiling
```

A refit preserves hierarchy topology, so extreme deformation can reduce traversal efficiency.

# 23. Buffer Addressing Options

## 23.1 Global heap offsets

```cpp
position =
    GlobalPositionBuffer[
        geometry.positionOffset +
        vertexIndex];
```

Advantages:

* compact geometry records;
* fewer descriptors;
* coherent global allocation.

Disadvantages:

* allocator complexity;
* potentially large address spaces;
* format variation requires care.

---

## 23.2 Bindless buffer handles

```cpp
BufferHandle positionBuffer;
uint positionOffset;
```

Advantages:

* flexible asset ownership;
* independent buffers;
* easier streaming.

Disadvantages:

* larger metadata;
* descriptor indexing requirements;
* potentially less coherent access.

---

## 23.3 Buffer device addresses

```cpp
uint64 positionAddress;
uint64 indexAddress;
```

Advantages:

* direct pointer-style access;
* flexible layouts;
* excellent for heterogeneous geometry.

Disadvantages:

* API capability requirements;
* alignment and lifetime hazards;
* more difficult validation.

Recommended Q3DE strategy:

```text
RHI interface:
    abstract GPU buffer reference + byte offset

Backend:
    global heap, bindless descriptor or device address
```

# 26. Ray Cones and Texture Filtering

Hardware barycentrics reconstruct UV coordinates but not ordinary screen-space derivatives.

Ray-traced texture sampling therefore needs another method.

Recommended initial approach:

```text
Primary visibility:
    raster derivatives or reconstructed screen derivatives

Secondary rays:
    ray cones
```

A ray-cone state may contain:

```cpp
struct RayCone
{
    float width;
    float spreadAngle;
};
```

At a hit, estimate texture footprint using:

* ray-cone width;
* triangle geometry;
* UV gradients across the triangle;
* hit distance.

Triangle UV gradients can be derived from:

```text
p0, p1, p2
uv0, uv1, uv2
```

This information is reconstructed externally and does not need to be stored in the BLAS.

---

# 27. Geometric Derivative Reconstruction

Given object-space edges:

```cpp
float3 dp1 = p1 - p0;
float3 dp2 = p2 - p0;
```

And UV edges:

```cpp
float2 duv1 = uv1 - uv0;
float2 duv2 = uv2 - uv0;
```

Calculate tangent-space derivatives:

```cpp
float determinant =
    duv1.x * duv2.y -
    duv1.y * duv2.x;

float reciprocal =
    1.0 / max(abs(determinant), epsilon);

float3 dpdu =
    (dp1 * duv2.y -
     dp2 * duv1.y) * reciprocal;

float3 dpdv =
    (dp2 * duv1.x -
     dp1 * duv2.x) * reciprocal;
```

Degenerate UV triangles require a fallback tangent basis.

# 28. Cache and Locality Considerations

This architecture trades BLAS duplication for external buffer reads.

To make it effective:

* keep triangle indices contiguous;
* keep attributes aligned by the same vertex index where possible;
* group nearby triangles into nearby memory;
* avoid random per-triangle pointer chains;
* keep geometry records compact;
* sort or group rays where practical;
* use coherent material and geometry layouts;
* reconstruct only requested attributes.

The likely access sequence is:

```text
Instance table
    ↓
RT geometry mapping
    ↓
Geometry record
    ↓
Three triangle indices
    ↓
Three values from each requested attribute stream
    ↓
Material record
```

The first implementation should profile each stage separately.

---

# 29. Optional Triangle Metadata Cache

For heavily traced static geometry, Q3DE may optionally precompute compact per-triangle metadata outside the BLAS.

```cpp
struct TriangleMetadata
{
    uint3 indices;
    uint materialID;
};
```

This avoids loading three independent index values plus a material mapping.

However, it duplicates index information.

Use it only when profiling shows that the duplication improves ray-shading performance enough to justify memory cost.

The baseline design should use the canonical index buffer directly.

---

# 30. Optional Precomputed Geometric Normals

Static mesh geometric normals could be precomputed per triangle:

```cpp
struct PackedTriangleNormal
{
    uint packedNormal;
};
```

This avoids fetching three positions when only the geometric normal is needed.

Again, this is an optional cache outside the BLAS.

The design should permit these caches but not require them.

---

# 31. Any-Hit Cost Control

Any-hit shaders can become expensive because they execute during traversal.

Rules:

1. Mark genuinely opaque geometry as opaque.
2. Keep alpha-test material data compact.
3. Fetch only UV and opacity data.
4. Avoid full material graph execution.
5. Avoid normal and tangent reconstruction.
6. Avoid arbitrary texture chains.
7. Use a specialised opacity program.
8. Prefer micromap-style hardware features later where supported.

Opacity evaluation should have a separate restricted interface:

```cpp
float EvaluateOpacity(
    uint materialID,
    float2 uv);
```

# 33. Slang Interface Example

```cpp
interface ISurfaceHitProvider
{
```

Raster implementation:

```cpp
struct RasterSurfaceHitProvider
    : ISurfaceHitProvider
{
    SurfaceHit GetSurfaceHit()
    {
        return DecodeVisibilityBuffer();
    }
};
```

RT implementation:

```cpp
struct RayTracingSurfaceHitProvider
    : ISurfaceHitProvider
{
    SurfaceHit GetSurfaceHit()
    {
        return DecodeRayTracingHit();
    }
};
```

Shared material code:

```cpp
SurfaceData surface =
    ResolveSurface(
        provider.GetSurfaceHit(),
        requestedAttributes);

BSDFData bsdf =
    EvaluateMaterial(surface);
```

This prevents raster and RT material reconstruction from diverging.

---

# 34. Shader Execution Choices

## 34.1 Traditional closest-hit shaders

Closest-hit shader:

1. receives hardware hit;
2. constructs `SurfaceHit`;
3. reconstructs requested attributes;
4. evaluates the material;
5. spawns or reports further rays.

Simple, but divergent material execution may be expensive.

---

## 34.2 Ray queries

Ray queries can return compact hit data to compute or pixel shaders.

The calling shader then performs reconstruction.

Useful for:

* shadows;
* reflections;
* GI probes;
* ReSTIR visibility;
* hybrid raster/RT passes.

---

## 34.3 Deferred ray shading

A future path may separate traversal from shading:

```text
Trace rays
    ↓
Write compact hit records
    ↓
Sort/group hits
    ↓
Reconstruct surfaces
    ↓
Evaluate materials
```

Compact hit record:

```cpp
struct DeferredRayHit
{
    uint instanceID;
    uint geometryID;
    uint primitiveID;
    uint packedBarycentrics;

    float hitDistance;
    uint rayIndex;
};
```

This closely mirrors visibility-buffer rendering and may improve coherence for large ray batches.

It is not required for the initial implementation.

---

# 35. BLAS Build Flags

Per BLAS, select flags according to usage:

```text
Static geometry:
    prefer fast trace

Animated geometry:
    allow update
    balance build/update cost and trace quality

Frequently rebuilt procedural geometry:
    prefer fast build where necessary
```

Do not enable update support for every static BLAS because it can increase memory consumption or reduce traversal quality.

---

# 36. Instance Transform Policy

TLAS instance transforms should normally represent rigid object transforms.

BLAS-local positions remain object space.

For skinned characters:

```text
Compute skinning:
    mesh/object-space positions

BLAS:
    object-space skinned positions

TLAS instance:
    world transform
```

This avoids applying world transforms to every skinned vertex.

Previous object transforms remain in the instance table for temporal reconstruction.

---

# 37. Multi-Mesh Skeleton Instances

A character may contain:

* body;
* armour;
* clothing;
* hair;
* equipment.

Each mesh may have its own BLAS or geometry range while sharing:

* animator state;
* skin matrices;
* object transform.

The ray hit maps through its own geometry record into the shared surface database.

No animation data is stored in the BLAS.

# 39. Validation

The engine should validate that:

* BLAS primitive ordering matches geometry-table primitive ordering;
* BLAS geometry ordering matches RT mapping records;
* position buffers remain alive for the BLAS lifetime;
* index buffers remain alive when required by the API;
* geometry offsets remain in bounds;
* primitive IDs remain below primitive counts;
* decoded indices remain below vertex counts;
* barycentrics are finite;
* dynamic position writes complete before BLAS updates;
* BLAS updates complete before tracing;
* material mappings are valid.

Debug shaders should output a visible error material instead of reading invalid memory.

# 40. Synchronisation

## 40.1 Static geometry build

```text
Position/index upload writes
    ↓
Transfer-to-AS-build barrier
    ↓
BLAS build
    ↓
AS-build-to-ray-tracing barrier
```

## 40.2 Animated geometry

```text
Compute skinning writes
    ↓
Compute-to-AS-build barrier
    ↓
BLAS update/refit
    ↓
AS-build-to-ray-tracing barrier
    ↓
Ray traversal
```

## 40.3 External attribute updates

If external attributes are modified:

```text
Attribute-buffer storage writes
    ↓
Shader-read barrier
    ↓
Surface reconstruction
```

External shading buffers do not require a BLAS rebuild unless position or topology changes.

# 43. Acceptance Criteria

The system is complete when:

1. A static BLAS is built using only positions and triangle topology.
2. Hardware hits return valid instance, geometry and primitive IDs.
3. Hardware barycentrics reconstruct UVs correctly.
4. Geometric normals reconstructed from external positions are correct.
5. Shading normals and tangents reconstruct correctly.
6. Materials resolve without being stored in the BLAS.
7. Opaque shadow rays require no attribute reconstruction.
8. Alpha-tested rays fetch only opacity-relevant data.
9. Raster visibility and RT hits use the same `SurfaceHit`.
10. Raster and RT use the same surface resolver.
11. Skinned positions can update an animated BLAS.
12. Static UVs and material data remain external for animated meshes.
13. Previous positions remain external and support motion vectors.
14. Geometry-table ordering remains consistent with BLAS geometry ordering.
15. No full vertex structure is duplicated solely for ray tracing.

# 44. Final Architecture

```text
GPU geometry database
    ├── positions
    ├── indices
    ├── normals
    ├── tangents
    ├── UVs
    ├── colours
    └── materials

            positions + indices
                    │
                    ▼
                  BLAS
                    │
              hardware trace
                    │
                    ▼
       InstanceID + GeometryIndex
      + PrimitiveIndex + Barycentrics
                    │
                    ▼
           RT geometry mapping
                    │
                    ▼
             GeometryRecord
                    │
                    ▼
          Fetch triangle indices
                    │
                    ▼
      Fetch only requested attributes
                    │
                    ▼
       Barycentric interpolation
                    │
                    ▼
          Shared SurfaceData
                    │
                    ▼
       Shared material evaluation
```

The optimisation can be summarised as:

> Hardware ray tracing determines which triangle was hit and where it was hit. Q3DE then reconstructs only the surface data required by that ray.

The BLAS remains a traversal structure, not a material or complete-vertex-data container.
